# ADR 1: MLflow through a local server
Status: accepted
Context: The course README logs to ./mlruns, which fails with mlflow 3.17.2. Logging straight to sqlite:///mlflow.db works for runs, but artifacts then go to ./mlruns with absolute paths and the artifact root setting is ignored, so the registry would hold paths tied to one machine and folder.
Decision: Run a local MLflow server on 127.0.0.1:5001 (port 5000 is taken by the system on this machine) with sqlite:///mlflow.db as the backend store and ./mlartifacts as the artifact destination, serving artifacts through the server. Clients use MLFLOW_TRACKING_URI=http://127.0.0.1:5001 only. mlflow is pinned to 3.17.2. The server is started with make mlflow-server.
Consequences: Training and the API need the server running. Artifact paths stay relative to the server's destination, so the registry is portable. One more process to start; the sqlite file and mlartifacts/ stay git-ignored and need a separate backup. Changing the version needs a new ADR. The server has no login, so anyone who can reach it can register or replace models. It must only listen on 127.0.0.1; never 0.0.0.0. A container reaches it through host.docker.internal, which needs a new ADR.
